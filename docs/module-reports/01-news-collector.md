# Повторный QA: 01 — News Collector

**Статус: PARTIAL.** Проверены интерфейс, fixture-сбор, каталог источников и локальные тесты. Ручной сетевой RSS-сбор в этом проходе не запускался, поэтому доступность RSS-серверов и запись в рабочую БД живым сбором не подтверждены.

## Назначение и владелец кода

Модуль разбирает RSS/Atom, нормализует публикации, отмечает полноту текста и сохраняет элементы с дедупликацией. Каноническая реализация находится в `modules/01-news-collector/backend/news_collector.py`; совместимость старых импортов обеспечивает `drive_data_analysis_2026-10-20/news_collector.py` (тонкая обёртка). Адаптер Studio — `modules/01-news-collector/backend/adapter.py`; собственный экран — `modules/01-news-collector/frontend/ModulePage.tsx`.

- Разрешённый список двух RSS-источников и ограничения запроса: `modules/01-news-collector/backend/news_collector.py:30-79`.
- Разбор даты, полноты текста, URL и устойчивого ID: там же, `:147-212`.
- Сетевой запрос имеет тайм-аут 25 секунд и ограничение ответа 8 МБ: `:30-32,215-224`.
- SQLite-схема, уникальность по источнику/GUID и нормализованному URL: `:227-267`; обновление/дедупликация записи: `:269-304`.
- Интервал опроса, раздельная обработка ошибок каждого источника, журнал запусков: `:318-374`.
- Fixture-адаптер использует временную SQLite-БД; live-адаптер сохраняет в отдельную локальную БД Studio `data/news_collector_studio.sqlite3`: `modules/01-news-collector/backend/adapter.py:8-9,33-76`.
- Результат показывает тип текста, публикации, ссылку, пропуски дат и долю выдержек: `modules/01-news-collector/frontend/ModulePage.tsx:4-18`.

## API и формат данных

Общий API Studio использует версию контракта `1.0`: `GET /api/modules/news-collector/health`, `/scenarios`, `/sources`; `POST /run` и `/tests`. Общая маршрутизация и формирование оболочки ответа находятся в `shared/backend/modules_api.py:162-197,228-301`.

Fixture-запрос содержит `mode`, `scenarioId` и/или `input` с `feed_key`, `rss_xml`, `repeat_first`. Live-сбор принимает `mode=live_feed` и выбранный `feed_key`; произвольный URL не принимается — источник сверяется с разрешённым списком (`adapter.py:11-16,52-56`). Успешный `/run` возвращает `contractVersion`, `module`, `mode`, `status`, `data`, `provenance` и `validation`; происхождение отдельно помечает `synthetic RSS`/временную БД либо публичный RSS/локальную БД (`modules_api.py:279-291`, `adapter.py:47-49,60-75`).

`GET /sources` показывает реестр и историю без запроса к ленте (`adapter.py:19-30`). При открытии страницы UI также сообщил, что источники не опрашиваются автоматически.

## Проверка интерфейса в Chromium

Проверка выполнена через Playwright в Chromium, `1440×1100`, адрес `http://127.0.0.1:5173/studio/news-collector`.

1. Открыл экран: backend был доступен; увидел два разрешённых источника и число сохранённых публикаций в отдельной локальной базе Studio. Сбор не запускался при открытии.
2. Режим по умолчанию был `Live RSS — ручной сбор`. Переключил на `Fixture`, оставив выбранный подготовленный сценарий `RSS и повтор`, чтобы не отправлять сетевой запрос.
3. Нажал `Запустить алгоритм`. Ответ API — HTTP 200, статус `PASS`; происхождение — synthetic RSS, внешних вызовов 0, временная SQLite.
4. На экране были 2 записи, 2 новых элемента и 1 точный повтор; полных текстов 0, без даты 1, неполных RSS-выдержек 2. Обе записи были помечены как выдержки; у одной отображалась дата, у второй дата отсутствовала. Ссылки на оригиналы отрисованы, но в этом проходе не открывались.
5. Нажал `Запустить 3 теста`: все три сценария (`RSS и повтор`, `Пустой RSS`, `Без даты`) получили PASS.

Наблюдение: неполная выдержка и отсутствующая дата видны прямо в пользовательском результате, не только в JSON. Fixture маркирован как синтетический, поэтому PASS не выглядит подтверждением живой доставки.

## Проблемы и приоритеты

**P2 — живую интеграцию RSS не подтверждали.** Это ограничение текущего QA, не обнаруженная ошибка продукта. Воспроизведение: выбрать `Live RSS — ручной сбор` и нажать `Собрать выбранную RSS-ленту`; действие намеренно не выполнялось, поскольку оно отправляет сетевой запрос и записывает историю в рабочую БД Studio. Перед эксплуатацией проверить источник отдельно с разрешённым сетевым запуском либо изолированным тестовым fetcher. Сейчас подтверждены только код и тесты с подменённым fetcher.

Иных ошибок в проверенном fixture-сценарии не обнаружено. Пересечения с пользовательской БД не наблюдалось: fixture-путь использует временную базу; исходные данные проекта не менялись.
