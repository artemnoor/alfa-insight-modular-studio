# 01 — News Collector: повторный пользовательский отчёт

**Проверка:** 22 октября 2026 г., Chromium / Playwright CLI. Повторная проверка исправлений выполнена на телефоно-подобном viewport 390×844.
**Итоговый статус:** **PASS** для проверенных пользовательских сценариев. Два ранее найденных дефекта Studio исправлены и повторно проверены в браузере.
**Режим AI:** сборщик не использует AI. T08/T09 принадлежат модулю News Intelligence. В этом проходе AI-вызовов не было.

## 1. Назначение, владелец и поток данных

Модуль загружает разрешённую RSS-ленту, извлекает публикации, нормализует ссылки и даты, определяет полноту текста, сохраняет записи и подавляет точные повторы. Это реальный RSS-клиент и парсер, не генеративный ответ. В Fixture-режиме алгоритм разбирает переданный XML тем же кодом, но временная БД изолирована.

Владелец алгоритма — `modules/01-news-collector/backend/news_collector.py`. Старый путь `drive_data_analysis_2026-10-20/news_collector.py` служит совместимой обёрткой. Studio-адаптер — `modules/01-news-collector/backend/adapter.py`; экран — `modules/01-news-collector/frontend/ModulePage.tsx`.

Поток:

1. Экран загружает реестр разрешённых источников и журнал локальных запусков. При открытии страницы RSS автоматически не запрашивается.
2. В Fixture пользователь выбирает готовый RSS XML либо вводит свой. Алгоритм разбирает XML и выполняет upsert/дедупликацию во временной SQLite-БД; временная папка удаляется после запроса.
3. В Live RSS пользователь выбирает источник allowlist и вручную запускает запрос. Сервис выполняет один GET с тайм-аутом 25 секунд и лимитом ответа 8 МБ.
4. Ключ записи строится из источника и GUID либо нормализованного URL. Ограничения уникальности и upsert учитывают повторы.
5. UI показывает статус, найденные/новые/обновлённые/повторные записи, дату, качество текста, оригинальную ссылку, контроль качества и историю запусков.

Разрешённый единственный Live RSS сбор ниже записал только в локальную БД копии Studio:

`data/news_collector_studio.sqlite3` in the local working clone (this workspace-local path is not included in Git).

Исходные `drive_data_analysis_2026-10-20/news.sqlite3` и CSV не изменялись. Клиентские сведения не передавались.

## 4. Дефекты и повторная проверка исправлений

### P2 — старый результат оставался после смены Fixture-сценария — ИСПРАВЛЕНО

**Исходное воспроизведение:** запустить «RSS и повтор», затем выбрать «Пустой RSS», не запуская его. Ранее оставались видны две записи и один повтор при уже сменившихся полях.

**Исправление проверено в UI:** после выбора «Пустой RSS» предыдущий результат очистился немедленно, поля и описание соответствовали новой фикстуре. После переключения обратно на «RSS и повтор» отображались правильные XML и состояние готовности.

### P2 — некорректный XML показывался как техническая ошибка — ИСПРАВЛЕНО

**Исходное воспроизведение:** Fixture → «Свои данные» → `<rss><channel>` → «Запустить алгоритм». Ранее ответ был HTTP 503 с `ParseError`, а справа оставалось вводящее в заблуждение ready-состояние.

**Исправление проверено в UI:** ответ HTTP 400, текст говорит о некорректной структуре RSS/XML, предыдущее состояние результата очищено/помечено как ошибка. Traceback и технический класс исключения пользователю не показаны.

### Замечание — HTTP 400 отображается в консоли браузера

При ожидаемом отрицательном тесте Chromium DevTools отмечает HTTP 400 как неуспешный сетевой запрос. Пользовательский экран при этом корректно показывает безопасное пояснение и остаётся работоспособным. Это не дефект парсинга и не серверный traceback.

### Владелец, исполнение и контракты

Единственный владелец сбора/разбора/дедупликации — `modules/01-news-collector/backend/news_collector.py`; старый `drive_data_analysis_2026-10-20/news_collector.py` — тонкая совместимая обёртка. `adapter.py` в Fixture передаёт XML в `parse_rss`, создаёт SQLite во временной папке, запускает тот же `_upsert_item` и возвращает список, качество и происхождение до удаления временной папки. На run передаются `mode`, необязательный `scenarioId` и XML/параметры в `input`; успех возвращает `contractVersion`, `mode`, `status`, `data`, `provenance` и `validation`. Источники Live RSS ограничены allowlist; они не могут быть заменены произвольным URL.

### Обнаружение и исправление provenance

В первом HTTP-ответе Fixture поля `kind=synthetic RSS` и `externalCalls=0` сопровождались `sources=[https://www.cbr.ru/rss/RssPress]`, хотя XML был fixture-вводом и сетевого запроса не было. Парсер, дедупликация и feed-профиль не менялись. После изменения модульные 8 Python-тестов прошли. Дополнительный свежий Chromium POST подтвердил HTTP 200 и новое тело: `kind=fixture RSS/XML`, `sources=["RSS XML payload supplied to Fixture adapter"]`, `writes=temporary SQLite only`, `externalCalls=0`; footer UI отображает тот же тип. ## Раунд 3 — повторная проверка в Chromium (2026-10-22)

Этот проход заново открыл страницу в отдельной headed-сессии Chromium (`r3news`) и выполнил действия по интерфейсу. Сессия использовала локальный API `127.0.0.1:8097`; статус Studio и API при старте — HTTP 200. Живая RSS-кнопка не нажималась: этот режим пишет записи в SQLite рабочего клона. Внешний AI не нужен для сбора RSS и в этом проходе не вызывался.

### Как устроен рабочий путь

- Адаптер `modules/01-news-collector/backend/adapter.py` разрешает только `cbr_press` и `consultant_federal` из списка `news_collector.SOURCES`.
- В режиме Fixture API объединяет выбранный сценарий и пользовательские входы, затем вызывает `adapter.run`. Тот разбирает переданный XML через `collector.parse_rss`, для идемпотентного хранения временно создаёт SQLite в `TemporaryDirectory`, прогоняет записи через `collector._upsert_item` и читает результат обратно. Fixture не обращается к сети и не использует рабочую БД.
- В Live RSS `adapter.run_live` передаёт один разрешённый источник в `collector.refresh_news`, который вызывает `fetch_feed`, проверяет HTTP/лимит размера RSS, разбирает XML, обновляет записи по GUID или нормализованному URL и сохраняет журнал сбора в `data/news_collector_studio.sqlite3`. Live RSS остаётся операцией с записью в локальную базу.
- `news_collector.py` внутри `modules/01-news-collector/backend/` — единственный владелец разбора, нормализации даты/URL, модели `NewsItem`, хранилища и дедупликации. Старый `drive_data_analysis_2026-10-20/news_collector.py` — compatibility-wrapper к этому владельцу, второй реализации алгоритма нет.
- Метка содержимого зависит от источника и полноты текста: RSS `description` у КонсультантПлюс считается выдержкой; у источника ЦБ описание считается полным лишь начиная с настроенного порога длины. Поэтому короткие описания в фикстуре отображаются как «RSS-выдержка», даже если выбран источник ЦБ.

### Вывод

На уровне Fixture модуль работает настоящим RSS-парсером и временной SQLite, а не заранее сохранённым ответом. Повторный импорт, пустая лента и некорректный XML воспроизводимы через UI; Fixture не загрязняет рабочую базу. Ручной публичный fetch в третьем раунде намеренно пропущен, поэтому доступность RSS-источников в данный момент и поведение при реальном сетевом отказе этим проходом не подтверждены. Прежний CBR fetch был подтверждён в более раннем раунде. Отдельная рекомендация: явно развести в подписи данных «короткая RSS-выдержка» и «полный текст», потому что выбранный источник сам по себе не гарантирует полноту короткого описания.

## Раунд 4 — отдельный повторный аудит модуля (2026-10-22)

### Назначение и как работает

Модуль отвечает за чтение RSS/Atom источников, первичную очистку публикаций и хранение. T08/T09 здесь не запускаются: UI направляет AI-классификацию в News Intelligence.

- Единственный владелец алгоритма — modules/01-news-collector/backend/news_collector.py. В нём заданы два источника allowlist, модели FeedSource и NewsItem, функции parse_rss (RSS item и Atom entry), fetch_feed (тайм-аут HTTP 25 секунд и максимум ответа 8 MB), _upsert_item, refresh_news, list_news и collector_history. Идентичность публикации проверяется по GUID источника или нормализованному URL; совпавшие материалы не дублируются, а более полная версия может обновить существующую. Fixture разбирает переданный XML, создаёт SQLite во временной папке, повторно использует _upsert_item, возвращает строки и удаляет временную БД. Provenance сообщает fixture RSS/XML, временное хранилище и ноль внешних вызовов. Live RSS проверяет ключ по allowlist, вызывает refresh_news(force=True) и по умолчанию сохраняет публикации и журнал в постоянную workspace DB.
- shared/backend/modules_api.py публикует контракт v1: /api/modules/news-collector/{health,scenarios,sources,run,tests}. В этом проходе UI на 127.0.0.1:5173 проксировал вызовы локальному Python API на 127.0.0.1:8097.
- modules/01-news-collector/frontend/ModulePage.tsx задаёт форму и отображение метрик, карточек, источника, полноты, ошибок и журнала. Общий shared/frontend/ModuleWorkbench.tsx управляет режимом, запуском и набором сценариев.

### Найденные дефекты и исправления

1. **P2 — fixture URL выглядел настоящим. Исправлено.** Тестовые записи содержат https://fixture.invalid/..., но UI предлагал открыть оригинальную публикацию. Теперь зарезервированный домен показывается как «Синтетическая ссылка (не оригинальная публикация)» без клика. Настоящие URL по-прежнему открываются обычной ссылкой.
2. **P2 — дата публикации показывалась ISO строкой. Исправлено.** Например, 2026-10-20T10:00:00+00:00 теперь отображается как «20 окт. 2026 г., 13:00» по локали и часовому поясу браузера; нераспознанная дата сохраняет исходное значение.
3. **P2, общий слой — старый результат после редактирования XML. Исправлено.** После PASS на «RSS и повтор» изменение XML теперь очищает предыдущий результат и возвращает форму в ready до нового запуска. Это подтверждено в Chromium; ошибка нового некорректного ввода показывается отдельно в области результата без traceback.
4. Во время прежнего параллельного прохода Chromium временно зафиксировал Vite 500 на HMR файла модуля 03 и 502 на `/api/modules`; последующий fixture модуля 01 снова получил HTTP 200. Это было transient-состояние совместной разработки. Итоговый build, полный suite и повторный Chromium E2E после изменений прошли.
